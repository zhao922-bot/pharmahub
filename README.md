# 药枢 PharmaHub

**中文药物作用机制学习伴侣** —— 把每一个药物的作用机制讲透、画出来、并帮你记住。

面向药学 / 生物制药专业学生、备考药师资格证的考生，以及工作几年想重拾药理的从业者。
用「机制卡片 + 机制图解 + 间隔重复」三件套，让人理解药物在分子层面做了什么，而不是死记硬背。

### 每个账号独立保存什么

- **复习进度**：掌握程度自评、SM-2 复习状态、下次复习日期、复习历史、连续学习天数和学习热力图。
- **收藏**：自己的药物卡片收藏清单。
- **测验与错题**：自己的答题记录、正确率、错题本和错题重练记录。
- **数据导出**：CSV / JSON 仅导出当前登录账号的记录。

药物卡片、机制图、对比内容和参考资料由大家共用；个人学习记录按账号隔离。新账号从空白个人记录开始，不会继承其他人的进度。同一账号在不同设备共用记录；不同账号在应用内互不查看、修改或清空对方的记录。未登录会跳转到 ChatGPT 登录，个人数据导出接口拒绝匿名访问。

- **数据库由谁托管**：云端版通过 Sites 托管，Cloudflare D1 由平台代为开通和绑定，不是每位访客个人 Cloudflare 账户中的数据库。站点项目所有权不等于底层 Cloudflare 账户所有权；当前应用未提供底层账户注册主体、存储地区或备份保留期限的确认信息。

## 安全运行验收

先在没有开发服务运行时执行 `pnpm build`，再运行：

```bash
pnpm verify                         # 全部 17 个浏览器脚本
pnpm verify -- verify-review         # 只跑错题重练
pnpm verify -- verify-stage3 verify-stage4
pnpm verify -- --list                # 查看可选脚本
```

统一入口会为**每个脚本**分配独立端口、临时 SQLite 数据库和生产服务，
结束后清理自己创建的服务与临时目录。日常使用的 3000 端口和学习数据库不参与验收。
只有局域网验收会监听所有网卡，其他验收只监听本机地址。
离线脚本通过入口启停自己的服务，不再调用日常停止脚本。
直接执行 `node scripts/verify-*.mjs`、`walkthrough.mjs`、`check-diagrams.mjs`
或 `shoot.mjs` 会拒绝运行并提示使用统一入口。

截图仍输出到 `.preview/`。数据库使用系统临时目录；正常结束、
失败和可处理的中断都会清理。强制结束整个 Node 进程或系统断电无法保证清理。

### 没有 Chrome 或安装位置不同时

自动验收支持 Chrome、Microsoft Edge、Chromium，路径集中由
`scripts/browser-path.mjs` 发现，顺序如下：

1. `BROWSER_PATH` 手动配置；兼容旧的 `CHROME_PATH`。
2. 系统登记位置：Windows 的 HKCU/HKLM App Paths（32/64 位），macOS 的 Spotlight。
3. `PATH` 中的浏览器可执行文件。
4. 常见安装目录作为兜底。

因此安装在 D 盘、用户目录等位置的已登记浏览器也可自动找到。
便携版、未登记或不在 PATH 的浏览器可以直接配置，无需移动安装目录：

```powershell
# Windows PowerShell：替换为自己实际的可执行文件路径
$env:BROWSER_PATH = 'D:\工具\Microsoft Edge\Application\msedge.exe'
pnpm verify
Remove-Item Env:BROWSER_PATH
```

```bash
# macOS / Linux
BROWSER_PATH="/custom/location/chromium" pnpm verify
```

找不到兼容浏览器或显式路径无效时，验收会报出配置方法，不自动安装软件，
也不会把未运行的检查报告为通过。Firefox、Safari 可用于日常浏览，
本套自动验收目前仅覆盖上述 Chromium 系浏览器。
跨平台路径解析有单元测试；Windows 之外的整套端到端运行仍需在目标系统验收。

## 在手机上使用

可以，而且不需要安装任何东西。

### 怎么用

1. 双击 `启动药枢.vbs`，日志目录会生成 `logs/status.txt`，里面写着手机访问地址：

   ```
   本机访问   http://localhost:3000
   手机访问   http://192.168.1.3:3000
   ```

2. 手机连**同一个 Wi-Fi**，浏览器打开上面那个地址。
3. 在浏览器菜单里选「添加到主屏幕」，之后就能像 App 一样打开。

### 能装成 App 吗

能。项目内置了 PWA（Progressive Web App）支持：

- `public/manifest.json` 声明了名称、图标、启动方式
- `public/sw.js` 提供 Service Worker
- `app/offline/page.tsx` 是断网兜底页
- 图标由 `scripts/gen-icons.mjs` 生成（不依赖 sharp 等库，用 Node 内置 zlib 手写 PNG 编码）

装到主屏幕后：

| 能力 | 是否支持 |
| --- | --- |
| 全屏运行（无浏览器地址栏） | ✅ |
| 主屏幕图标与启动画面 | ✅ |
| 离线查看已访问过的页面 | ✅ |
| 离线时看已缓存的内容 | ✅ |
| **离线时写复习记录** | ❌ 见下 |

### 离线为什么不能写数据

复习记录、错题本、收藏都存在**运行服务的电脑**上的 SQLite 里。
断网后手机连不上那台电脑，写操作必然失败。

硬要做离线写入，需要在浏览器里再实现一套 IndexedDB 存储加同步逻辑，
两套数据源迟早会不一致。这个取舍我选了不做——断网时直接说明情况，
而不是让用户以为记录保存了。

离线页会明确告诉用户：什么还能用，什么要等联网。

| 项目 | 结果 |
| --- | --- |
| 局域网访问全部路由 | 9/9 可用，无横向溢出 |
| server action 跨网络 | 收藏、复习记录都能写入 |
| 安装引导 | 移动端显示，桌面端不显示 |

### 关于 Service Worker 的一个坑

`puppeteer` 的 `setOfflineMode()` 和 `setRequestInterception()` 都会**绕过 Service Worker**。

实测用探针记录过：断网导航时 SW 只收到 `/manifest.json`，页面请求根本没到 SW。
所以用这两种方式测「离线降级」，测的其实是 Next.js 的错误边界行为，
结论必然是错的（会看到 `(self.__next_f=...).push([0])` 这样的原始脚本被当正文渲染）。

唯一可靠的验证方式是：让 SW 先接管页面，然后**真的把服务器停掉**，再导航。
这就是 `scripts/verify-offline.mjs` 的做法——它会自己启停服务器。

### 局域网连不上怎么办

按顺序排查：

1. **手机和电脑是否在同一 Wi-Fi**——手机用流量、电脑连网线就不在同一网络。
2. **防火墙是否放行**——Windows 安全中心 → 防火墙 → 允许应用通过防火墙 → 勾选 Node.js。
3. **是不是连了 VPN**——VPN 会改变路由，先断开再试。
4. **地址是否写对**——注意是 `http://` 不是 `https://`，端口 `3000` 不能漏。

## 为什么用 VBS 而不是 BAT

`.bat` 双击必然弹出控制台窗口，即使写了 `start /min` 也会闪一下。
更麻烦的是 `next start` 会作为子进程**重新申请一个控制台**，
任务栏上就出现「next-server (v14.2.35)」窗口——这就是之前那个弹窗的来源。

VBS 的 `WScript.Shell.Run(cmd, 0, False)` 用窗口样式 `0` 启动，全程无窗口。
但仅这一层还不够：PowerShell 里 `Start-Process -WindowStyle Hidden` 只隐藏 cmd 自己，
子进程仍会拿到窗口。所以 `scripts/server-start.ps1` 里改用
`ProcessStartInfo.CreateNoWindow = $true`，从进程创建层面就不分配控制台。

### 停止脚本不再误杀其他 Node 程序

旧版用 `taskkill /F /IM node.exe`，会杀掉机器上**所有** Node 进程——
你同时开着的编辑器插件、其他项目、甚至别的工具都会被一起杀掉。

新版按「命令行里包含本项目路径」精确匹配，只终止本项目的进程。

### 踩过的三个坑

1. **PowerShell 把字符串里的 `>>` 当重定向解析。**
   `$cmd = "pnpm start >> log 2>&1"` 会报 `StreamAlreadyRedirected`，
   即使它在双引号里、甚至在注释里。解决：用 `[char]62 + [char]62` 拼出符号。

2. **PowerShell 5.1 靠 BOM 识别 UTF-8。**
   没有 BOM 的 `.ps1` 会被按系统 ANSI 代码页解析，中文全乱码。
   `.ps1` 必须存成 UTF-8 **with BOM** + CRLF。

3. **VBS 必须 GBK 编码 + CRLF。**
   Windows Script Host 按系统 ANSI 代码页解析 `.vbs`，
   UTF-8 会让 `MsgBox` 文字变乱码。

## 间隔重复是怎么实现的

### 算法

采用 SM-2（SuperMemo 2），Anki 等记忆软件的基础算法。

三档自评到 SM-2 六级评分的映射：

| 自评 | SM-2 quality | 效果 |
| --- | --- | --- |
| 没记住 | 2 | 连续次数归零，间隔重置为 1 天，难度因子 −0.32 |
| 模糊 | 3 | 次数 +1，难度因子 −0.14 |
| 记住了 | 5 | 次数 +1，难度因子 +0.10 |

间隔规则：第 1 次答对 1 天，第 2 次 6 天，之后 `上次间隔 × 难度因子`。
难度因子下限 1.3，防止间隔无限缩短。

> **与标准 SM-2 的差异**：标准算法用 0~5 六级评分，本项目按产品需求只用三档，
> 因此 quality 4（犹豫后正确）没有对应选项，「模糊」映射到 3 而非 4。
> 这会让间隔增长略慢于标准 SM-2——属于偏保守的取舍，宁可多复习一次。

### 连续学习天数

从今天（或昨天）往前数连续有复习记录的天数。
**今天还没复习但昨天复习了，streak 仍然保留**——否则用户每天早上打开应用
都会看到归零，体验不合理。

### 数据表

```sql
review_log     -- 每张卡片一行，当前复习状态（下次到期日、难度因子、间隔）
review_history -- 每次复习一行，用于统计今日复习数与连续天数
favorite       -- 收藏
```

用 `review_history` 而不是只更新 `review_log`，是因为「今日复习数」和
「连续学习天数」都需要历史，单表无法回溯。

### 为什么详情页从静态改成了动态

阶段二的详情页是构建期预生成的静态页。阶段三要读取 SQLite 里的复习记录，
这份数据随用户操作实时变化——若继续静态预渲染，用户复习后刷新会看到过期状态。
因此详情页与首页改为 `force-dynamic`。

代价是失去静态预渲染，但卡片内容仍在内存中，每次请求只有一次轻量 SQLite 查询。

### Cloudflare 迁移

云端迁移已在 [online 分支](https://github.com/zhao922-bot/pharmahub/tree/online) 完成并上线；该分支使用按账号隔离的 D1 数据层。下面说明本地版迁移涉及的范围。

`main` 分支的 `lib/db/sqlite.ts` 是**整个项目唯一直接依赖 Node 与 better-sqlite3 的地方**，
且标注了 `server-only`，不会被打包进客户端。迁移到异步数据库时，
除连接适配层外，还需重写 `lib/data/study.ts`、`lib/data/quiz.ts`、
`lib/data/export.ts` 中的同步 SQL 调用与事务实现。仓库对外已返回 Promise，
可保持对页面暴露的接口稳定；不能把迁移理解成只替换一个文件。

## 搜索是怎么做的

### 为什么不只是 includes

最初的搜索是 `searchText.includes(keyword)`，只能覆盖药名、英文名、商品名、靶点和适应症。
但学药理时想找的东西往往在别处：

- 「cAMP 减少的药有哪些」→ 答案在机制步骤正文里
- 「哪个药会乳酸性酸中毒」→ 答案在不良反应里
- 「β1」和「beta1」是同一个东西，但字符串不等

所以改成了三层：**归一化 → 字段加权评分 → 命中定位**。

### 归一化

搜索前把查询与正文都归一化，四件事：

| 处理 | 例子 | 为什么要做 |
| --- | --- | --- |
| 全角转半角 | `ＡＢＣ` → `abc` | 中文输入法容易打出全角 |
| 希腊字母转写 | `β1` → `beta1` | 打 β 比打 beta 麻烦得多 |
| 繁体转简体 | `受體` → `受体` | 港澳台用户与旧教材常用繁体 |
| 丢弃空白 | `β1 受体` → `beta1受体` | 让带不带空格都能搜到 |

归一化时保留「归一化字符 → 原文下标」的映射。这一步很关键：
`β` 转成 `beta` 是 1 个字符变 4 个，如果直接用归一化后的下标去切原文，
截出来的片段就会错位。有了映射才能精确地在原文上截取并高亮。

### 字段加权

不同字段命中，代表的相关性差别很大：

| 字段 | 权重 | 理由 |
| --- | --- | --- |
| 通用名 | 100 | 输入药名显然就是要找这张卡 |
| 英文名 | 90 | 同上 |
| 商品名 | 85 | 同上 |
| 作用靶点 | 60 | 高频检索维度 |
| 适应症 | 50 | 高频检索维度 |
| 机制步骤 | 40 | 本次新增 |
| 分类 | 30 | 检索意图较弱 |
| 不良反应 | 25 | 本次新增 |
| 记忆要点 | 20 | 本次新增 |

同一字段内再按命中位置加成：完全相等 > 前缀命中 > 中间命中。
这样搜「二甲双胍」时，药名命中的卡片会稳定排在「正文里提到二甲双胍」的卡片前面。

### 命中定位

搜索结果不只告诉用户「这张卡匹配」，还告诉他**匹配在哪**：

```
机制  第 3 步
…苷酸环化酶不被活化，细胞内 cAMP 生成减少，蛋白激酶 A 的活…
```

用户能直接判断是不是自己要找的卡，不用点进去翻。
同时右侧显示「另有 N 处命中」，提示这张卡还有别的地方也提到了关键词。

### 多词查询是 AND

输入「阻断 受体」时，要求两个词都命中。这符合常见搜索框的直觉——
如果改成 OR，加词反而会让结果变多，用户会困惑。

### 与服务端共用同一套逻辑

`lib/search` 是纯函数、无 React 依赖。客户端 `CardBrowser` 与服务端
`cardRepository.getSummaries({ keyword })` 调用的是同一批函数，
所以「本地即时过滤」与「服务端查询」结果必然一致。
两处各写一份实现，迟早会漂移。

### 校验

```bash
node --test --experimental-strip-types --import ./scripts/ts-alias-hook.mjs scripts/search.test.mjs
# 或直接 pnpm test（运行全部单元测试）
```

25 项测试覆盖归一化、分词、评分排序、AND 语义、片段截取与高亮区间。
测试直接 import 真实 TS 源码，不是把逻辑复制一份——复制一份等于测了个假货。

## 测验题是怎么生成的

### 为什么是自动生成

63 张卡片 × 每张 2~3 道手写题 = 100 道以上，内容工作量不小，而且卡片一旦修改
题目就会失配。自动生成的好处是**永远与卡片内容同步**，加卡片就自动有新题。

代价是题目模板化，所以做了两件事来弥补：题型覆盖四个角度（见下），
以及每题都配解析——解析不是复述答案，而是把这道题对应的机制环节讲一遍。

### 四种题型

| 题型 | 考什么 | 干扰项来源 |
| --- | --- | --- |
| 作用靶点 | 药物作用于谁 | 其他药物的真实靶点 |
| 机制顺序 | 因果链哪一步在前 | 同一张卡片的其他步骤 |
| 适应症 | 临床用途 | 其他药物的真实适应症 |
| 所属分类 | 知识体系归属 | 其他系统分类名 |

**关键约束：干扰项必须是真实的**。所有错误选项都取自其他药物的真实靶点、
适应症或分类，不存在编造的假选项。这样即使选错，读到的也是正确知识。

「机制顺序」是唯一直接考察因果链理解的题型——只背下靶点名称答不对它。

### 确定性与出题分布

用自实现的 mulberry32 伪随机数生成器，以 `seed` 为输入。同一个 seed
永远生成同一组题，所以刷新页面、答错重练时题目不会突然变样。

出题分布上踩过一个坑：最初按「卡片外层、题型内层」轮转，结果同一张卡片
连出四道题（靶点→顺序→适应症→分类），前三题就把后面的答案泄漏了。
改成**外层按题型轮转、内层每次换卡片**后，相邻题目考的必然是不同药物。

### 校验

```bash
node --test --experimental-strip-types --import ./scripts/ts-alias-hook.mjs scripts/quiz.test.mjs
```

### 错题重练

答错的题进入错题本后，可以在 `/quiz/review` 只针对错题组卷重练。

**实现上有一个关键取舍：错题本不存题干和选项，只存稳定题目 id。**
普通题为 `cardId:kind`；对比题为 `compare:groupId:quizId:cardId`，
因此同一种药在不同对比维度答错时分别保留记录。

理由有三：

1. **不会内容过期**。卡片内容修订后（比如某个机制步骤写得更准确了），
   重练题会自动用上新内容，不会出现「题干说的是旧版机制」这种不一致。
2. **省存储**。一道题 4 个选项加上题干和解析，几百字节；只存 id 是几十字节。
3. **便于重建**。服务端可用题目身份重新生成内容；对比题提交时还会校验
   分组、维度、卡片和选项，并以重建题目的答案判分。

代价是重练时选项顺序由 `cardId:kind` 派生种子决定——这是**故意的**：
同一道错题每次重练选项顺序一致，用户不会因为选项换位置而误选。
如果每次随机，反而会让人怀疑「上次我选的是这个位置吗」。

**出题顺序按错误次数降序**。错得最多的排最前面，正好是最该练的。
这个顺序沿用 `wrong_question` 表的排序，出题层不打乱。

**答对后不删除记录**，只写 `last_correct_at`。错题的价值在于反复巩固，
答对一次就消失反而让人失去复盘线索。界面上会标「已答对过」，由用户自己决定何时移除。

校验：

```bash
node --test --experimental-strip-types --import ./scripts/ts-alias-hook.mjs scripts/review-quiz.test.mjs
pnpm verify -- verify-review               # 端到端 12 项
```

单元测试覆盖：四种题型都能从卡片重建、重建是确定性的、题目 id 格式与错题本一致、
卡片已删除时安全跳过、重复记录只出一次、机制步骤不足时跳过而非生成残缺题。

### 按分类出题

`/quiz?category=nervous` 只考该分类的卡片。两个实现细节值得记：

**1. 干扰项仍取自全部卡片。** 如果限定分类后干扰项也只从该分类里挑，
「所属分类」这种题型就退化了——4 个选项全是「神经系统」，
用户不用思考也能排除。所以 `cards` 传的是筛选后的卡片，`allCards` 传的是全量。

**2. 分类参与种子计算。** 种子由「日期 + 小时」生成，如果分类不参与，
切换分类后题目会与「全部」高度重合。这里用 FNV-1a 把分类 id 映射成稳定的整数偏移。

筛选用链接而不是客户端状态，所以 URL 可分享、刷新后仍在同一分类。

### 按对比组练习

从任意对比详情页点「练习本组差异」，或在测验页「按对比组练习」中选组。
例如 `/quiz?compare=acei-vs-arb`；同时带分类参数时以对比组为准。
未知或空对比 id 显示不存在页面，不回退到全部卡片。

- 题干引用对比行的描述，选项为本组 2～3 种药名，解析列出同一维度各药的描述。
  七轮扩充的二十八组另有 `quizExplanation` 解释区别和易错点，答题与错题重练共用。
- `CompareRow.quizId` 是人工选定的可考维度标记与稳定身份。共 120 个维度，
  每轮每个维度只考一次，目前每组 2～5 题，不重复凑满 8 题。
- 共同点、适用场景和易混淆的维度不自动转成单选题。只比较文字不同不足以认定
  医学含义互斥；后续新增 `quizId` 时需人工判断。旧八组内容保持原状。
- 组内轮流选所考药物，题序受 `seed` 控制；「再来一组」保留本组并更换种子。
  可考维度有限，下一轮可能复现题目，不承诺每轮全新。
- 原题 id 固定为 `compare:groupId:quizId:cardId`，改行序不影响错题身份。
  已发布的 `quizId` 不要改名或复用。删除的维度会在重练时跳过，旧记录仍保留。
- 对比题与原有四种题型共用答题记录、错题本与 CSV/JSON 导出，不需数据库迁移。
  错题本显示原组与维度，解析提供「回看本组对比」入口。

核心实现：`lib/quiz/compare-generator.ts`；数据入口：`lib/data/compares.ts`。

## 学习数据导出

`/export` 可以把复习记录、测验记录、错题本、收藏导出为 CSV。
底层是 `/api/export/[kind]` 这个 Route Handler。

### 为什么用 Route Handler 而不是 Server Action

Server Action 无法触发浏览器下载——它只能返回数据，再由客户端造 Blob 存盘。
用 `GET` + `Content-Disposition: attachment` 更直接，浏览器的「链接另存为」也能识别。

### CSV 的两个坑

**1. Excel 中文乱码。** Windows 版 Excel 默认按 GBK 解析 CSV，
文件开头没有 UTF-8 BOM 时中文会变成乱码。所以输出以 `\uFEFF` 开头。

**2. CSV 注入。** 以 `=` `+` `-` `@` 开头的单元格会被 Excel 当成公式执行。
虽然本项目的数据都来自自己的卡片，理论上不会出现恶意内容，
但这属于「防御成本极低、出事代价很大」的类型，所以统一加前导单引号阻断。

转义遵循 RFC 4180：含逗号/双引号/换行的字段用双引号包裹，内部双引号写成两个。
换行用 CRLF，这也是 Excel 最稳的选择。

### 内容可读性

导出的列同时包含 **id 和中文名**：id 用于程序分析，中文名用于人阅读。
如果卡片已被删除（错题本可能比卡片数据活得久），药名列填「（卡片已删除）」
而不是留空，避免用户以为导出出错。

### 两种格式：CSV 与 JSON

`/api/export/{kind}?format=csv|json`，格式用 query 参数而不是独立路径，
这样「同一份数据的不同序列化」在语义上保持在一起。

**关键设计：先组装结构化记录，再序列化。**

最初的实现是「直接拼 CSV 行」，加 JSON 时就得把每个 builder 抄一遍。
两份逻辑必然漂移——改了一处忘另一处，或者两处字段名不一致。现在改成：

```
数据查询 → ExportDataset（列定义 + 记录对象） → CSV / JSON 序列化
```

数据只查一次、字段只定义一次，两种格式天然一致。
序列化部分拆到 `lib/export/serialize.ts`（纯函数），
因为 `build.ts` 带 `server-only`，单元测试无法导入。

JSON 结构：

```json
{
  "exportedAt": "2026-10-19T02:30:00.000Z",
  "kind": "reviews",
  "count": 3,
  "columns": [{ "key": "reviewedAt", "header": "复习时刻" }],
  "records": [{ "reviewedAt": "...", "genericName": "美托洛尔" }]
}
```

带上 `columns` 是有意的：脚本处理时需要知道字段的中文含义，否则只能靠猜。
同时 `records` 里的 key 是稳定的英文标识，便于写代码。

**两种格式的语义差异**（这是刻意的，不是不一致）：
CSV 里布尔值转成「是/否」便于阅读；JSON 里保持 `true/false` 便于程序判断。
数值同理：CSV 里难度因子是字符串 `"2.50"`，JSON 里是数字 `2.5`。

### 校验

```bash
pnpm test                              # 包含 CSV 18 项、序列化 20 项
pnpm verify -- verify-export-filter    # 端到端 21 项
pnpm verify -- verify-json-heatmap     # 端到端 39 项
```

一个踩过的坑：验证 BOM 时不能用 `res.text()`。
按规范 `Response.text()` 在解码时会**剥离** UTF-8 BOM，
`charCodeAt(0)` 拿到的是正文首字而不是 `\uFEFF`。必须检查原始字节 `EF BB BF`。

## 同类药对比

`/compare` 把散落在各张卡片里的横向差异摆到一张表上。

卡片是「纵向」的（一个药讲透），对比是「横向」的（多个药在同一维度上的差异）。
比如丙硫氧嘧啶与甲巯咪唑的区别（是否抑制外周 T4→T3），
在卡片里要读两遍才能对比出来，对比视图把它变成一行。

### 数据结构

```ts
interface CompareGroup {
  id: string;            // 用于路由
  title: string;         // 「第一代 vs 第二代抗组胺药」
  summary: string;       // 一句话说清这组比的是什么
  drugIds: string[];     // 2~4 个，顺序决定列顺序
  rows: { label: string; values: string[]; quizId?: string; quizExplanation?: string }[];
                        // values 长度必须等于 drugIds 长度；共同点不设置 quizId
  takeaways: string[];   // 关键差异，1~3 条
  scenarios?: string[];  // 选药场景
  sources?: { title: string; url: string; sections: string }[];
  sourcesCheckedOn?: string;  // 本组资料核对日期
}
```

**维度由每组自定义，不用全局固定维度。** 抗组胺药关心「是否进脑」，
抗真菌药关心「抑菌还是杀菌」，强行统一会导致大量空白。

### 移动端的关键取舍：不用 `<table>`

3 个药 × 8 个维度在 375px 下无法做成传统表格——每列只有 90px，
药名稍长就换行成三四行，整张表失去可读性。

改成「按维度分组的卡片流」：每个维度一张小卡，卡内纵向列出各药取值。
每个取值都能拿到整行宽度，内容不会被挤压。

代价是失去「横向扫视一列」的能力。补偿方式：每个取值前加药名标签，
并用不同颜色的**左侧色条**区分药物——扫视时靠颜色定位，比靠位置更快。

### 一个 CSS 陷阱

色条最初用 `border-l-amber-500`，结果渲染成灰色。

原因：父级 `<ul>` 用了 `divide-y divide-border/60`，Tailwind 的 `divide-*`
会设置子元素的 `border-color`，优先级与 `border-l-*` 相同但后声明，
把彩色左边框覆盖成灰色。

换成独立的绝对定位 `<span>` 色条后绕开了这个冲突。
`verify-compare.mjs` 里有一条专门的回归检查，断言色条不是灰色。

### 校验

```bash
node --test --experimental-strip-types --import ./scripts/ts-alias-hook.mjs scripts/compare.test.mjs
pnpm verify -- verify-compare          # 端到端 24 项
```

数据校验（`check-compares.mjs`，已并入 `pnpm check:cards`）检查 8 项，
其中最关键的是**每个维度的 `values` 长度必须等于 `drugIds` 长度**——
少写一个值表格就错位，而 TypeScript 查不出来（`values` 只是 `string[]`）。

单元测试还额外断言「每组至少有一个维度取值存在差异」——
如果所有维度都相同，这组对比就没有意义。

## 学习热力图

首页展示近 26 周的复习活跃度，一列一周、纵向周一到周日。
计算逻辑在 `lib/review/heatmap.ts`（纯函数，27 项单元测试）。

### 三个不显然的取舍

**1. 从周一开始，不是周日。** JS 的 `getDay()` 是周日 = 0，
直接用会让整张图错位一天。用 `(getDay() + 6) % 7` 转成周一 = 0。

**2. 未来日期不画格子。** 画成灰色空格会被误读成「那天没学」，
实际是「还没到」。所以未来日期是 `null`，渲染时留空。

**3. 移动端初始滚动到最右。** 26 周 × 7 天 = 182 格，375px 下每格约 9px。
格子保持固定尺寸（可读性优先），容器横向滚动。
但用户最关心最近的日期，所以用 `dir="rtl"` 让滚动原点落在右边，
内层再设回 `ltr` 保证时间顺序仍是左到右——纯 CSS，不需要客户端 JS 去 `scrollTo`。

### 等级阈值不是等分的

1 / 4 / 8 / 12 次作为分界，而不是按最大值等分。
因为实际使用中「一天复习 1~3 张」是常态，等分会让大多数日子挤在最低档，看不出差异。

### 两处连续天数必须一致

首页进度卡的「连续天数」用 `calculateStreak`（SM-2 模块），
热力图用 `buildHeatmapGrid`。算法不同（一个查 Set，一个扫网格），
但结果必须一致，否则用户会看到两个互相矛盾的数字。
有 3 项测试专门断言两者相等。

两者都遵循同一条规则：**今天还没学但昨天学了，不算断签**。
否则每天早上打开应用都会看到「连续 0 天」。

## 深色模式

三态：浅色 → 深色 → 跟随系统，选择存在 `localStorage`。

两个技术点：

1. **首屏防闪烁**：在 `<head>` 里内联一段同步脚本，React 水合前就设置好
   `.dark` 类。否则深色用户每次打开都会先看到白屏闪一下。
2. **机制图不重渲染**：SVG 里的颜色不写死，改用 CSS 自定义属性
   （`var(--ph-target-fill)` 等）。浅色与深色两套值都写进同一段 `<style>`，
   切主题只改根元素的类，服务端不需要为两种主题各渲染一遍。

## 机制图是怎么画的

这是阶段二的核心，值得单独说明。

### 数据与渲染分离

卡片里只存 `DiagramSpec`——**语义结构**，不存任何坐标：

```ts
diagram: {
  title: "β1 受体阻断：从心肌到血压",
  nodes: [
    { id: "drug", label: "美托洛尔", role: "drug" },
    { id: "b1",   label: "β1 受体",  role: "target" },
    { id: "camp", label: "cAMP ↓",  role: "signal" },
    ...
  ],
  edges: [
    { from: "drug", to: "b1", label: "阻断", kind: "inhibit" },
    ...
  ],
}
```

坐标由 `lib/diagram/layout.ts` 在构建期计算。这样新增一张卡片只需要写内容，
不需要手绘 SVG；调整样式也只改一个地方，全部机制图同时生效。

### 布局算法

1. **分层**：用最长路径分层确定每个节点在第几层（药物 → 靶点 → 信号 → 效应）。
   同层节点横向均分，节点宽度按文字长度自适应。
2. **走线**：相邻层走「竖直—水平—竖直」折线；跨层连线走右侧专用通道绕行，
   避免穿过中间层的节点文字。
3. **标签避让**：连线标签按自身方向选锚点（分叉线推向目标一侧），
   再做矩形相交检测，冲突则上下微调。绕行线的标签贴通道放置，
   否则读者无法判断它属于哪条线。

### 可读性设计

- 画布逻辑宽度 360，用 `viewBox` 自适应，375px 手机上字号约 12px
- 节点文字超长自动换行（最多 2 行），而不是缩小字号
- **激活/抑制不只靠颜色区分**：激活是实线+箭头，抑制是虚线+平头，色觉障碍用户也能分辨
- SVG 带 `role="img"` 和 `aria-label`，屏幕阅读器可获知图意
- 服务端渲染，不向客户端发送 JS

### 校验

```bash
pnpm verify -- check-diagrams   # 需已有生产构建，入口自动启动独立服务
```

用 Puppeteer 逐张检查每个 SVG 内所有文字的外接矩形是否相交、是否溢出画布。
卡片 id 由脚本自动扫描种子数据文件获得，新增卡片自动纳入校验。

## 架构说明

### 数据层为什么是异步的

卡片数据目前来自本地 TypeScript 种子文件，同步即可获得。但 `lib/data` 的接口统一声明为
`Promise`，因为未来迁移到 PostgreSQL 或 CMS 时必然是异步的。页面只依赖
`CardRepository` 接口，迁移时只需新增一个实现类并切换 `lib/data/cards/index.ts`
的导出，**调用方一行都不用改**。

### 本地版运行时约束（main 分支）

- 页面主要为服务端组件；学习状态相关路由使用动态渲染。
- 本地版使用 SQLite 和文件系统，需要 Node.js 运行时及持久化目录。
- 本地版不能原样静态导出或上传到 Cloudflare Workers。已上线的 `online` 分支完成了 Vinext 适配、D1 数据访问与事务改造，并添加了登录和用户数据隔离。

### 文案集中管理

所有面向用户的文字都放在 `lib/copy.ts`（界面文案）与 `lib/data/cards/*`（卡片内容）中，
组件内不硬编码中文。这样繁体自查只需扫描固定的目录：

```bash
pnpm check:zh
```

脚本内置 341 个「繁体专用字 → 简体字」对照表，命中即报错并指出文件与行号。
对照表只收录繁体专用字形（如「藥」「樞」「學」），不收录简繁同形字（如「查」「效」），
避免误报。

## 数据模型

```ts
interface DrugCard {
  id: string;                    // 稳定英文 id，如 "metoprolol"
  genericName: string;           // 通用名：美托洛尔
  brandNames: string[];          // 商品名（只保留最常用的 1~2 个）
  englishName: string;           // Metoprolol
  category: CategoryId;          // 所属分类
  target: string;                // 作用靶点一句话
  mechanismSteps: { title: string; detail: string }[]; // 3~6 步
  indications: string[];         // 临床主要适应症
  adverseReactions: string[];    // 机制相关的不良反应 3~5 条
  memoryTip: string;             // 记忆要点
  diagram: DiagramSpec;          // 机制图描述（供 SVG 渲染）
  needsVerification?: boolean;   // 内容待核实标记
  verificationNote?: string;     // 待核实说明
}
```

`DiagramSpec` 只描述图的语义结构（节点角色 + 连线类型），不涉及具体绘制：

- 节点角色：`drug`（药物）/ `target`（靶点）/ `signal`（信号）/ `effect`（效应）
- 连线类型：`activate`（激活，箭头）/ `inhibit`（抑制，平头）

现有渲染器按「DiagramSpec → SVG」生成机制图，卡片数据不保存布局坐标。

## 内容准确性

- 按条目列出的公开说明书与指南核对关键结论，记录具体章节、制剂范围与日期；不能将来源齐全或缺省标记解释为专业医学审定
- 机制正文可含并行作用、药代和风险说明；不得为了凑顺序题把假说或并行事件写成严格因果链。机制题只读取经单独核对的 `mechanismQuiz`
- 已知未确认事项通过 `needsVerification` 标记并说明具体范围；缺少该标记不代表所有医学问题已经排除
- 内容仅供学习参考，不构成用药建议

## 如何新增卡片

加一张卡片只需**改一个文件**，不需要碰任何索引、路由或搜索代码。

### 步骤

**1. 在对应分类文件末尾追加对象**（如 `lib/data/cards/digestive.ts`）：

```ts
{
  id: "mesalazine",              // 稳定的英文 id，全库唯一，用于路由与复习记录关联
  genericName: "美沙拉嗪",
  brandNames: ["艾迪莎"],         // 没有公认商品名就写 []
  englishName: "Mesalazine",
  category: "digestive",
  target: "一句话说清作用位点",
  mechanismSteps: [ /* 3~6 步，每步 title + detail */ ],
  indications: [ /* 3~4 条 */ ],
  adverseReactions: [ /* 3~5 条，优先写机制相关的 */ ],
  memoryTip: "一句话口诀",
  diagram: { title, nodes, edges },
}
```

**2. 同步文件头注释里的张数**：

```ts
/**
 * 消化系统 · 7 张卡片    ← 改成新的数量
 */
```

**3. 跑校验**：

```bash
pnpm check:cards
```

### 会自动生效的部分

以下全部**不需要手动改**，因为都是从这个数组推导出来的：

| 功能 | 推导方式 |
| --- | --- |
| 卡片库列表与详情页 | `index.ts` 用数组展开自动收录 |
| 全文搜索 | `buildSearchIndex` 遍历全部卡片建立索引 |
| 测验出题 | 从 `cardRepository.getAll()` 取卡片，干扰项自动从其他卡片挑 |
| 分类筛选 | 按 `category` 字段过滤 |
| 首页分类角标 | `getCategoryCounts()` 实时统计 |
| 机制图 | `check-diagrams.mjs` 自动发现卡片 id |

### 校验会拦住什么

`pnpm check:cards` 会依次跑四个脚本：

- **`check-card-counts.mjs`** — 注释里的张数与实际是否一致
- **`check-content.mjs`** — 机制步骤 ≥3 步、适应症与不良反应非空、机制图连通性
- **`check-card-ids.mjs`** — id 唯一、`index.ts` 已引入全部文件
- **`check-compares.mjs`** — 对比分组、关联卡片与维度值校验

还有一个不在这个命令里的：`pnpm verify -- check-diagrams` 会启动浏览器逐张渲染机制图，检查文字重叠与溢出。它比较慢，所以没放进 `check:cards`。

### 如何新增一个分类

比加卡片多改三处，但都不涉及业务逻辑：

**1. `lib/types.ts`** — 在 `CATEGORY_IDS` 数组末尾加 id：

```ts
export const CATEGORY_IDS = [
  // ...
  "respiratory",
  "antiallergic",
] as const;
```

**2. `lib/data/categories.ts`** — 加一条分类定义：

```ts
{
  id: "respiratory",
  name: "呼吸系统",
  summary: "一句话说明这个系统的学习重点。",
  order: 8,   // 决定首页与筛选条的展示顺序
},
```

**3. 新建 `lib/data/cards/respiratory.ts`** 并在 `index.ts` 里 import + 展开。

界面无需改动：首页分类区用 `grid sm:grid-cols-2`，筛选条用横向滚动，都是自适应的。

**踩坑提醒**：`check-card-ids.mjs` 会检查「`index.ts` 已引入全部文件」。如果新建了分类文件却忘了 import，这个检查会拦住——但它只检查文件名是否出现在 import 语句里，不会检查数组是否展开。两处都要改。

### 三个容易踩的坑

**1. 机制图的连线标签不能重复。** 两条边如果写一样的 label，布局算出的位置会重合，`check-diagrams.mjs` 会报「文字重叠」。标签要能区分（比如「传导下降」和「胆碱能占优」）。

**2. 机制图要连通。** `check-content.mjs` 要求 `edges >= nodes - 1`，否则图会断成两块。

**3. 卡片 id 一旦发布就不要改。** 复习记录、错题本、收藏都用 id 关联。改了 id 会让用户的历史数据变成孤儿（导出时会显示「（卡片已删除）」）。

### 关于文件编码

源文件统一用 **UTF-8 无 BOM + LF 换行**。

这一条要特别提醒：`check-content.mjs` 用正则匹配 `\n      {\n        title:`，如果文件被保存成 CRLF，正则就匹配不到，会误报「机制步骤只有 0 步」。

曾经有 17 个文件因为用 Python 脚本批量编辑被转成 CRLF，导致这个检查全部误报。**编辑源码时优先用编辑器或 `edit` 工具，避免用会重写整个文件的脚本。**

## Cloudflare 部署

### 已上线的云端版本

[正式站点](https://pharmahub.ampleox17.chatgpt.site) 使用 `online` 分支，通过 Sites 托管 Vinext 应用，由 Cloudflare Workers 执行，Cloudflare D1 保存个人学习数据。该站点已向其他 ChatGPT 账号开放；应用仍要求登录，并在每次数据访问时按当前用户 ID 查询或写入。

云端版已完成以下工作：

- 保留卡片、机制图、测验与对比内容，将本地 SQLite 访问替换为 D1 数据层。
- 为复习状态、复习流水、收藏、测验记录和错题添加用户归属；服务端身份来自 ChatGPT 登录，不由前端指定。
- 对并发复习使用版本检查和重试，收藏切换及测验流水使用原子操作或事务，避免多设备写入丢失记录。
- 通过 `db/schema.ts` 和 `drizzle/` 管理数据库迁移；生产与本地预览数据库分开，个人数据库不进入 Git 仓库。
- 保留个人 CSV / JSON 导出和登录校验，并将统计日期统一为 UTC+8。

开发、构建和迁移命令见 [online 分支 README](https://github.com/zhao922-bot/pharmahub/blob/online/README.md)。日常使用只需打开正式网址，不需要执行部署命令。

### 保留的本地版本

`main` 分支仍使用 `better-sqlite3`，不能原样作为静态站点或 Cloudflare Worker 部署。它需要可长期运行的 Node.js 进程及可写的持久化磁盘，数据库路径可通过环境变量指定：

```bash
PHARMAHUB_DB_PATH=/var/data/pharmahub.db pnpm start
```

该变量已由 `lib/db/sqlite.ts` 实现，仅影响本地版。修改它不会导入、覆盖或同步线上 D1 数据。将本地版托管到其他 Node 平台的具体流程尚未验收。
